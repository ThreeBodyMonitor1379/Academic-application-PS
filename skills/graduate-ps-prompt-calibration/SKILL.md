# 以官方 prompt 裁决研究生申请文书的实际任务

先解释目标项目真正要求申请者回答什么，再决定内容重心、语气与开头。把 PS、SOP 和 application essay 当作可能含义不稳定的标签，不把标签、旧范例或通用 handout 升级为目标项目的规则。

只使用用户提供、可从官方来源核验或由用户确认的事实。不得猜测申请者经历、研究兴趣、身份、困难、教师联系或项目资源；缺少事实时保留空位、提出最小必要问题或交接到相邻 skill。

## I — 方法论骨架（Interpretation）

1. PS、SOP 和 application essay 的名称不能稳定地定义写作任务；实际任务由目标项目当期的具体题目与官方补充说明决定。
2. 校准的分析单位不是“这类文书通常怎样写”，而是题目中的指令动词、必答对象、限制、受众和提交情境。
3. 先区分硬性要求、由文本支持的推断和仍待确认的问题；不得把推断伪装成要求。
4. 来源发生冲突时，优先采用更具体、更当前且直接控制该申请入口的官方信息，并把仍无法消解的冲突显式留给用户确认。
5. 过去／未来、个人／学术、叙事／直接等比重应由题目要评估的判断驱动，而不是由 PS 或 SOP 标签驱动。
6. hook 与直接开头都是条件选项；只有在服务必答任务并能进入未来方向时，开头才有功能。
7. 最终产物是一份带来源的写作约束简报，而不是跨项目通用模板，也不是对申请者事实的补写。
8. 当题目证据不足时，正确结果可以是“暂不能裁决 + 缺失信息清单”，而不是自信猜测。

## A1 — 来源中的既往应用（Past Application）

本 handout 没有机构作者亲身申请的案例，也没有录取结果。以下三项是其 **handout illustrative examples / FAQ 对照**；它们只能证明决策方式，不能证明采用某种写法会提高录取概率，也不能成为当前用户的素材。

### 案例 1：PS 与 SOP 的定义冲突

- **问题**：常见来源分别用“个人历史／未来工作”和“自传叙事／直接学术表达”区分 PS 与 SOP，两套定义不能互相裁决。
- **使用**：FAQ 拒绝给标签设唯一含义，转而要求查看目标机构对写法与内容的说明。
- **结论**：先读取实际 prompt，再决定体裁任务；文件名只是一条低强度线索。
- **结果**：得到“机构与 prompt 优先”的判断规则；材料未报告真实申请或录取结果。

### 案例 2：个人化与专业化语气

- **问题**：申请者可能把语气误解成“越故事化越独特”或“越客观越专业”的二选一。
- **使用**：FAQ 把语气放在 anecdotal 到 direct 的连续谱上，并要求结合机构和学科情境避免极端。
- **结论**：语气必须服务题目要求与评审理解，而不能独立决定内容。
- **结果**：得到情境化语气选择；材料没有提供任何语气与录取结果之间的证据。

### 案例 3：personal hook 与直接开头

- **问题**：同一生物医学工程方向既可从个人经历进入，也可直接声明学术目标。
- **使用**：handout 并列两种说明性开头，并用“能否连接未来计划”作为共同检查点。
- **结论**：不强制故事式开头；应选择更能完成具体 prompt 任务的路径。
- **结果**：得到开头的功能性判据；示例身份与经历不属于作者或用户，也没有外部成效记录。

## A2 — 未来触发（Future Trigger）

### 触发场景

1. 用户提供了研究生申请文书的具体 prompt，想知道每个问句、动词和限制实际要求什么。
2. 文件被叫作 PS 或 SOP，但题目要求与用户理解的体裁印象冲突。
3. 申请门户、项目页面、院系 PDF 或 FAQ 给出的篇幅、内容或格式说明互相冲突，需要建立来源优先级。
4. 用户要根据目标题目决定个人经历、学术准备、未来目标和 programme fit 的相对重心。
5. 用户在 personal hook、直接开头、个人化或专业化语气之间犹豫，并希望先形成约束再起草。

### 语言信号

- “这个 prompt 到底在问什么？”“学校叫它 PS，但为什么全在问研究计划？”
- “PS 和 SOP 在这个项目里有什么区别？”“这几条官方要求冲突，听哪一条？”
- “这道题应该更 personal 还是更 academic？”“要不要用故事开头？”
- “What does this graduate statement prompt actually require?”
- “Should I treat this as a PS or SOP, and should the opening be personal or direct?”
- “Turn these official instructions into a writing brief before I draft.”

## E — 可执行步骤（Execution）

### 1. 建立来源账本，不先猜体裁

- 收集可用的精确 prompt、上传字段说明、当期项目页面／FAQ、申请周期、文档标签及明确格式限制。
- 若用户只给出可识别的项目而当前要求可能变化，先核验该项目当期官方来源；记录 URL、页面标题、适用周期和访问日期。
- 使用以下优先原则：直接控制该申请入口的当期官方题目与格式说明，高于更一般或更旧的官方指南；官方要求高于领域惯例；领域惯例高于本 CMU handout 的通用建议。
- **完成标准**：每条输入都有来源；未知、失效和冲突信息被单独列出，没有从 PS/SOP 标签补全缺失规则。
- **判停点**：若缺少精确 prompt，却要求机构特定的确定结论，先请求题目／官方链接，或在能识别项目时查找官方来源。仍找不到时只给“暂定判断 + 待确认项”，不要起草。

### 2. 把题目拆成可审计的要求

逐条建立要求矩阵：

| 字段 | 要回答的问题 |
|---|---|
| 来源与适用周期 | 这条要求来自哪里，是否控制当前申请？ |
| 原文与指令动词 | 题目原话是什么；要求 describe、explain、evaluate、reflect 还是 propose？ |
| 必答内容 | 明确要求哪些经历、目标、问题、准备或匹配？ |
| 硬限制 | 字数／字符、文件数、格式、禁止项和截止条件是什么？ |
| 证据类型 | 需要事实、反思、研究问题、未来计划还是机构资源？ |
| 状态 | `hard requirement`、`supported inference` 或 `open question`？ |

- 不把官方页面中的示例身份、教师、经历或研究主题写成用户事实。
- **完成标准**：每项 “must” 都能回指原文；每项推断都附理由与不确定性；无法回答的问题仍保持开放。

### 3. 裁决标签、冲突与体裁任务

- 用一句话改写实际任务，例如：“在给定上限内，用准备证据和未来问题回答研究匹配；个人背景仅在解释该方向时进入。”
- 对冲突依次比较：是否为当前周期、是否针对该项目、是否直接出现在提交入口、措辞是否明确。不能可靠消解时，不自行挑选最方便的版本；报告冲突，并建议用户向项目方确认，但不得代用户联系。
- 只有当 prompt 留出真实选择空间时，才使用领域惯例校准语气或开头；清楚的官方要求不被通用建议覆盖。
- **完成标准**：体裁结论来自任务文本而非标签；每个冲突都有“已裁决 + 依据”或“未裁决 + 下一步”。

### 4. 生成约束简报并路由后续工作

输出以下内容：

1. **任务判定**：题目希望评审据此判断什么。
2. **硬性约束**：逐条给出原文、来源和适用周期。
3. **内容地图**：`必须回答`、`条件加入`、`不要加入`，按题目优先级排序；不凭空制造固定百分比。
4. **语气与开头**：给出选择、证据和备选；无法裁决时明确需要的领域或机构信息。
5. **开放问题**：列出会改变写法但尚未确认的信息。
6. **交接建议**：按 A2 路由到编排器、trajectory、fit 或领域惯例 skill。

- **完成标准**：每项建议可追溯到官方要求、清楚标注的推断或用户事实；删除学校名称后仍成立的“官方要求”必须重新检查。
- **判停点**：除非用户同时要求起草且已有足够真实材料，否则在约束简报处停止。需要补充申请者内容时询问，不得替用户猜。

## B — 边界（Boundary）

### 不要使用或不要继续的情形

- 用户没有具体项目或 prompt，只问某领域的普遍写法、读者、篇幅或 jargon：使用 `field-role-audience-calibration`。
- 题目已经明确，用户只想把经历组织成发展轨迹：使用 `graduate-ps-trajectory-bridge`。
- 用户只想修复泛泛的 why programme 段：使用 `two-way-academic-fit`。
- 用户需要从事实材料到完整文书的端到端工作流：使用 `evidence-first-graduate-personal-statement`，本 skill 只提供前置约束。
- 非研究生申请文书、普通求职信、CV 栏目或推荐信，不属于本 skill。

### 禁止升级为通用规则的内容

- CMU handout 中的两页、教师数量、字号和边距数字只是其通用建议，不得硬编码；目标项目当期的具体 prompt 和官方格式始终优先。
- 不得仅凭 “personal statement” 或 “statement of purpose” 决定过去／未来比例、是否必须讲故事或是否必须点名教师。
- 不得把个人 hook 变成强制创伤叙事，也不得要求用户披露不必要的健康、家庭或身份信息。
- 不得捏造用户经历、研究目标、成绩弱项、项目资源、教师招生状态、通信记录或未来贡献。

### 来源警告与失败模式

- **单一模板**：先选一套所谓标准 PS/SOP 结构，再把 prompt 强塞进去。
- **标签代替任务**：引用文件名，却不引用题目中的实际指令。
- **通用指南覆盖官方要求**：用旧 handout 或范例否定当前项目的明确规则。
- **语气走极端**：故事性压过学术任务，或机械专业化抹去题目要求的反思。
- **证据越界**：把 FAQ 示例当作作者亲历、成功申请或当前用户事实。
- 来源为未标正式日期的美国机构 handout，示例偏研究导向，也没有招生效果数据；不得把其局部建议外推为所有国家、项目类型或周期的规则。
